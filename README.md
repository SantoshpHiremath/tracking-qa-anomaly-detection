# Webshop Tracking QA & Anomaly Detection Tool

A tested Python tool that generates a synthetic GA4/GTM-style e-commerce tracking event stream with deliberately injected tracking bugs, runs automated QA checks against it, aggregates it into daily metrics, and runs anomaly detection with root-cause triage hints. It covers web-analytics tracking QA and anomaly detection for a webshop.

## What it does

- **`src/events.py`**: synthetic tracking event generator with three injected bugs (below), plus a background 3% rate of missing `item_id` on view_item events (a data-quality baseline of everyday noise alongside the single clean bugs).
- **`src/tracking_qa.py`**: automated QA checks: missing required parameters (by event type), duplicate conversion-event detection, funnel-ordering consistency checks, and zero-event-day (outage) detection. These implement automated checks for missing or broken tracking parameters and support test cases for new tracking implementations.
- **`src/anomaly_detection.py`**: a rolling median + MAD (median absolute deviation) z-score anomaly detector, computed per market (each market gets its own baseline rather than one global threshold, since traffic volume varies a lot by market), plus simple root-cause triage hints based on directly observable signals (is the metric at zero? is it unusually high or low?).
- **`src/pipeline.py`**: runs the full flow end to end and prints QA findings, daily metrics, flagged anomalies, and root-cause hints.

## Data

All tracking event data is synthetic, generated by `src/events.py`. The event stream models a standard e-commerce funnel (page_view, view_item, add_to_cart, begin_checkout, purchase) across 5 markets over 60 days, with three deliberately injected, realistic tracking bugs:

1. **Missing currency parameter** on FR purchase events for a 7-day window (a common bug: a market-specific config never gets wired up).
2. **Duplicate purchase events** firing twice for US, for a 4-day window (a common bug: a page reload or misconfigured trigger double-logs a conversion).
3. **A silent tracking outage**: add_to_cart/begin_checkout/purchase events stop firing entirely for UK, for a 5-day window (a common bug: a tag fails to load, or a consent-mode change silently blocks it).

The checks and detector are built to run on real GA4/GTM exports in place of the synthetic stream.

## Results

All three injected bugs are caught by the appropriate check, confirmed with exact-match tests rather than by eyeballing the pipeline output:

- Missing currency (FR, 7 days): caught exactly by `check_missing_required_params`; the flagged market, event type, and date range match the injected bug exactly.
- Duplicate purchases (US, 4 days): caught by both `check_duplicate_events` (every flagged duplicate falls inside the bug's market/day window) and by anomaly detection on the `purchase` metric (clear positive z-score spikes on the affected days).
- Tracking outage (UK, 5 days): caught exactly by `check_zero_event_days` (all 5 days, UK only), and caught by anomaly detection on `add_to_cart` on the first day immediately and on at least 75% of the outage window overall (see Notes on the rolling baseline).

## Tests

25 automated tests (`tests/test_tracking_qa_anomaly.py`) covering: event generation determinism and realistic funnel shape, exact-match detection of all three injected bugs by their respective checks, no false positives outside the injected bug windows, MAD z-score correctness (including the flat-series and division-by-zero edge cases), daily metric aggregation correctness against manual recalculation, anomaly detector sanity bounds (flags a small minority of days, not everything or nothing), and root-cause hint generation.

## Running it

```bash
pip install pandas
python3 src/pipeline.py          # generates events, runs QA checks, aggregates metrics, runs anomaly detection
python3 -m pytest tests/ -v      # runs all 25 tests
```

## Notes

Three things I caught and fixed during development:

1. **Event volume**: the first version of the generator produced ~1.8 million events for a 60-day/5-market simulation, correct in shape but impractically large for a demo and slow to test. I rescaled market traffic volumes down by 10x (to ~180,000 events) without changing the funnel logic or bug-injection behavior.
2. **Session-ID collision**: the first version generated each event's `session_id` from a random draw (`rng.randint(0, base)`) within each market/day. With a few hundred possible values per market per day, two unrelated purchase events could land on the same synthetic session ID by chance (a pigeonhole problem, worse for smaller markets), producing a spurious "duplicate purchase" flag for UK on a day unrelated to the injected bug. A test asserting every flagged duplicate falls inside the actual bug's market/day window caught it, and I fixed it by generating session IDs from a running per-market/day/event-type counter instead of a random draw. `test_duplicate_purchase_bug_detected` guards it.
3. **Rolling-baseline behavior on sustained outages**: on a sustained outage, the anomaly detector's rolling 14-day baseline starts to include the outage's own earlier zero-value days as the outage continues, which pulls the baseline down and can shrink the z-score for the tail end of a long-running anomaly below the alert threshold. In this dataset, the 5-day UK outage is caught immediately on day 1 and on at least 75% of the window. `test_anomaly_detection_catches_tracking_outage` asserts "first day + most of the window," and the standard threshold is kept rather than tuned to this one dataset.

## Possible extensions

- Run the QA checks and detector on real GA4/GTM exports.
- Use a baseline that excludes already-flagged days to improve detection across long outages.
- Add alerting on the flagged anomalies.
