# Webshop Tracking QA & Anomaly Detection Tool

A real, tested Python tool that generates a synthetic GA4/GTM-style
e-commerce tracking event stream with deliberately injected tracking
bugs, runs automated QA checks against it, aggregates it into daily
metrics, and runs anomaly detection with root-cause triage hints — built
to close a specific gap for BIRKENSTOCK's "Working Student Global
Digital Analytics & BI" posting: web-analytics tracking QA and anomaly
detection, neither of which existed anywhere in my prior project
portfolio.

## What this is (read before citing anywhere)

**All tracking event data is synthetic**, generated by `src/events.py` —
not real BIRKENSTOCK webshop, Google Analytics, or GTM data. I have not
worked with a real GA4/GTM implementation. What's built here demonstrates
the underlying skill — designing tracking QA checks and an anomaly
detector, and verifying both actually work against known-injected
problems — on a system I could construct and test myself.

The event stream models a standard e-commerce funnel (page_view →
view_item → add_to_cart → begin_checkout → purchase) across 5 markets
over 60 days, with three deliberately injected, realistic tracking bugs:

1. **Missing currency parameter** on FR purchase events for a 7-day
   window (a common real bug: a market-specific config never gets wired
   up).
2. **Duplicate purchase events** firing twice for US, for a 4-day window
   (a common real bug: a page reload or misconfigured trigger double-logs
   a conversion).
3. **A silent tracking outage** — add_to_cart/begin_checkout/purchase
   events stop firing entirely for UK, for a 5-day window (a common real
   bug: a tag fails to load, or a consent-mode change silently blocks
   it).

## What this models

- **`src/events.py`** — synthetic tracking event generator with the
  three injected bugs described above, plus a background 3% rate of
  missing `item_id` on view_item events (an "always some noise" data-
  quality baseline, not a single clean bug to find).
- **`src/tracking_qa.py`** — automated QA checks: missing required
  parameters (by event type), duplicate conversion-event detection,
  funnel-ordering consistency checks, and zero-event-day (outage)
  detection — directly implementing "Build automated checks for missing
  or broken tracking parameters" and "design, document, and execute test
  cases for new tracking implementations."
- **`src/anomaly_detection.py`** — a rolling median + MAD (median
  absolute deviation) z-score anomaly detector, computed per market
  (each market gets its own baseline rather than one global threshold,
  since traffic volume varies a lot by market), plus simple, honest
  root-cause triage hints based on directly observable signals (is the
  metric at zero? is it unusually high or low?) — not a black-box
  diagnosis.
- **`src/pipeline.py`** — runs the full flow end-to-end and prints QA
  findings, daily metrics, flagged anomalies, and root-cause hints.

## Verified against the known-injected bugs (not just "it runs")

All three injected bugs are confirmed caught by the appropriate check,
checked with exact-match tests, not just eyeballing the pipeline output:

- Missing currency (FR, 7 days): caught exactly by
  `check_missing_required_params` — flagged market, event type, and date
  range match the injected bug exactly.
- Duplicate purchases (US, 4 days): caught by both
  `check_duplicate_events` (every flagged duplicate falls inside the
  bug's market/day window) and by anomaly detection on the `purchase`
  metric (clear positive z-score spikes on the affected days).
- Tracking outage (UK, 5 days): caught exactly by `check_zero_event_days`
  (all 5 days, UK only), and caught by anomaly detection on `add_to_cart`
  for the first day immediately and at least 75% of the outage window
  overall (see the note below on why not literally every single day).

## A note on three things caught and fixed during development

Documented here rather than silently fixed, because catching and fixing
them honestly is part of the evidence this project provides.

1. **Unrealistic event volume**: the first version of the generator
   produced ~1.8 million events for a 60-day/5-market simulation —
   correct in shape but impractically large for a portfolio demo and
   slow to test. Rescaled market traffic volumes down by 10x (to
   ~180,000 events) without changing the funnel logic or bug-injection
   behavior.
2. **Session-ID collision bug**: the first version generated each
   event's `session_id` from a random draw (`rng.randint(0, base)`)
   within each market/day. With a few hundred possible values per market
   per day, two unrelated purchase events could land on the same
   synthetic session ID purely by chance — a pigeonhole problem, worse
   for smaller markets. This produced a spurious "duplicate purchase"
   flag for UK on a day that had nothing to do with the injected
   duplicate-purchase bug. Caught by a test asserting every flagged
   duplicate falls inside the actual bug's market/day window (not by
   eyeballing the pipeline output), and fixed by generating session IDs
   from a running per-market/day/event-type counter instead of a random
   draw. Guarded by `test_duplicate_purchase_bug_detected`.
3. **Rolling-baseline contamination limitation (a real, documented
   limitation, not a bug)**: on a sustained outage, the anomaly
   detector's rolling 14-day baseline starts to include the outage's own
   earlier zero-value days as the outage continues, which pulls the
   baseline down and can shrink the z-score for the tail end of a
   long-running anomaly below the alert threshold. In this dataset, the
   5-day UK outage is caught immediately on day 1 and on at least 75% of
   the window, but not guaranteed on literally every day — this is
   disclosed and tested for honestly (`test_anomaly_detection_catches_
   tracking_outage` asserts "first day + most of the window," not "every
   single day"), rather than tuning the threshold specifically to make
   this one dataset look perfect, which would be circular and dishonest.

## Verification

25 automated tests (`tests/test_tracking_qa_anomaly.py`) covering: event
generation determinism and realistic funnel shape, exact-match detection
of all three injected bugs by their respective checks, no false
positives outside the injected bug windows, MAD z-score correctness
(including the flat-series and division-by-zero edge cases), daily
metric aggregation correctness against manual recalculation, anomaly
detector sanity bounds (flags a small minority of days, not everything
or nothing), and root-cause hint generation.

## Running it

```bash
pip install pandas
python3 src/pipeline.py          # generates events, runs QA checks, aggregates metrics, runs anomaly detection
python3 -m pytest tests/ -v      # runs all 25 tests
```
